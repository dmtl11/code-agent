# Code Agent 迭代开发简报

## 1. 项目目标

本项目从一个“把用户问题发送给大模型并显示回答”的 Demo，逐步升级为可以理解仓库、调用本地工具、修改和验证代码、保留会话记忆，并提供审查与监控能力的 Code Agent Harness。

核心执行链路为：

`用户 Query -> 恢复 Session -> 构建相关代码上下文 -> 调用 LLM -> 执行工具 -> 将结果返回 LLM -> 验证代码 -> 保存记忆、审查记录和监控数据 -> 返回结果`

## 2. 主要迭代

| 迭代 | 做了什么 | 什么用处 |
| --- | --- | --- |
| 1. 基础 LLM 调用 | 将用户 Query、系统提示词发送给模型，并显示模型回答。 | 验证模型连接、API Key、模型配置和基础问答链路。 |
| 2. ReAct Agent 循环 | 模型不再只回答一次，而是在“判断下一步 -> 调工具 -> 读取结果 -> 继续判断”之间循环，当前最大 24 轮。 | 让模型能分步骤完成较大的编码任务，并根据工具结果修正后续动作。 |
| 3. 文件与命令工具 | 加入 `list_files`、按行 `read_file`、`search_files`、`write_file`、`replace_in_file`、`run_command`、`lint_file`。 | Agent 可以查看目录、只读取相关代码片段、搜索定义、编辑文件、执行测试，并在无输出时得到明确结果。 |
| 4. 代码运行能力 | 网页编辑器支持保存文件，并可直接运行 Python；C++ 会先编译再运行。 | 产品不只是聊天界面，也具备基本编辑器和代码验证能力。 |
| 5. Repo Map | 自动提取 Python/C++/JS/TS 文件中的类、函数、方法和行号，并按 Query 相关度放入模型上下文。 | 减少模型盲目遍历文件的次数，以较少 Token 找到可能相关的代码。 |
| 6. 四种工作模式 | 提供 Code、Ask、Plan、Context；Ask 和 Plan 禁止写文件及运行命令。 | 将“直接修改”“仅回答”“先规划”“查看上下文”分开，降低误操作风险。 |
| 7. 上下文管理 | 保留近期对话，截断超长工具输出，压缩早期 Agent 步骤，并保证工具调用与工具结果成组保留。 | 避免长任务超过上下文窗口，也避免因残缺 `tool_calls` 历史导致模型返回 HTTP 400。 |
| 8. 多模型适配 | 支持 DeepSeek、Qwen，以及通过 CloseAI 中转的 ChatGPT 和 Claude；不同协议统一成内部消息与工具调用格式。 | 前端可以切换模型，同一套 Agent 工具不必为每个模型重复实现。 |
| 9. Session 持久化 | 用 SQLite 保存消息、结构化记忆、上下文检查点、工具调用状态；切换模型仍使用同一个 Session。 | 页面刷新或模型切换后能继续任务；进程中断后能识别未完成的工具调用。 |
| 10. Review 与合并 | Agent 每轮执行前后生成文件快照，Review 页面显示修改，并可合并多次连续变更。 | 用户可以在接受修改前看到具体影响，集中处理同一文件的多次修改。 |
| 11. 监控 | 记录模型请求数、Token、延迟、错误率、工具成功率、上下文压缩次数和近期错误。 | 可以判断 Agent 的成本、稳定性和最常失败的环节，为后续优化提供数据。 |
| 12. 界面可用性修复 | 修复文件点击、编辑器显示、聊天区域滚动、发送后输入框状态和模型身份显示。 | 保证长对话、连续提问和文件编辑等主要流程可以正常使用。 |
| 13. Windows 命令进程控制 | 明确 `cmd.exe` 语法，拒绝 `start /b`、裸 `&` 等后台服务命令；前台命令超时后终止进程组并返回明确结果。 | 避免 Node 等子进程长期占用输出管道，导致网页只显示一条进度消息后不再更新。 |
| 14. 32k 上下文预算 | 默认上下文从 16k 调整为 32k，历史消息预算提高到最多 8k，并动态预留最多 8k 输出空间。 | 长任务可以保留更多代码与工具结果，同时避免输入占满窗口后模型没有足够空间输出。 |
| 15. Auto 多模型路由 | 先根据用户输入识别通用、代码、数学或架构任务，再结合复杂度、上下文规模和近期工具失败，在 Qwen Flash/Coder/Math/Plus/Max、DeepSeek、ChatGPT 和 Claude 之间选择，并在调用失败时级联回退。 | 同一 Session 内自动匹配专用模型并平衡速度、成本、能力和可用性；路由选择与回退会进入聊天事件和监控指标。 |

## 3. 本次架构升级

### 3.1 持久化代码注册表

**做了什么：** 新增 `code_registry.py`，在工作区的 `.code_agent/code_registry.sqlite3` 中保存文件元数据、SHA-256、语言、类/函数符号、行号，以及 import/include/call 等关系。注册表会根据文件大小和修改时间增量更新，编辑后也会立即刷新。

**什么用处：** Repo Map 不再每次从零扫描和解析整个仓库。注册表是完整、可复用的代码事实层，后续可以继续增加引用查找、依赖图和跨文件影响分析。

### 3.2 Repo Map 改为相关投影

**做了什么：** `repo_map.py` 不再自己遍历文件，而是从代码注册表读取数据，根据 Query 对路径、符号和关系计算相关度，再在字符预算内生成紧凑上下文。

**什么用处：** “完整索引”和“送给模型的上下文”被分开。系统可以知道整个仓库，但只把当前任务最相关的部分交给 LLM，减少 Token 和噪声。

### 3.3 原子 Diff/Patch 编辑

**做了什么：** 新增 `apply_patch`，支持一个补丁同时新增、修改或删除多个文件；所有目标先完成上下文匹配和语法检查，再统一写入。任意文件失败时，整组修改都不落盘。

**什么用处：** 相比整文件覆盖和单段 `replace_in_file`，多文件修改更清晰，也不会出现“第一个文件已改、第二个文件失败”的半完成状态。

### 3.4 Dry Run 与冲突检测

**做了什么：** `apply_patch` 支持 `dry_run=true`；`read_file` 返回文件哈希，补丁可以携带 `base_hashes`。如果文件在读取后被用户或其他任务修改，Agent 会收到冲突而不是覆盖新内容。

**什么用处：** 高风险修改可先预演；哈希和唯一上下文匹配共同防止过期补丁误改代码。

### 3.5 补丁回滚

**做了什么：** 每次成功补丁都生成事务 ID，并在 `.code_agent/patches` 保存变更日志。`rollback_patch` 会先确认文件仍处于补丁后的状态，再恢复原内容。

**什么用处：** Agent 可以撤销自己刚完成的多文件修改；若用户已经继续编辑，则回滚会报告冲突，不会破坏用户的新代码。

### 3.6 完整 Review Diff 与网页回滚

**做了什么：** Session 数据库保存完整 unified diff、修改前后内容及文件存在状态。Review 页面直接显示真实 diff，并增加 `Rollback selected`；服务端对多文件回滚执行语法检查、冲突检测和失败恢复。

**什么用处：** 用户看到的是准确的逐行变化，而不是截断文件的近似对比；新增文件、删除文件和连续修改都能正确回滚。

## 4. 当前安全与可靠性边界

- 所有文件工具都限制在指定工作区内，拒绝路径逃逸。
- Ask/Plan 模式没有写文件和执行命令权限。
- Python 写入前使用 AST 做语法检查；Python/C++/JavaScript 可调用对应检查工具。
- `apply_patch` 要求修改上下文唯一匹配，并支持文件哈希冲突检测。
- 多文件补丁和 Review 回滚采用“先验证、后写入、失败恢复”的方式。
- 命令执行有超时和基础危险命令拦截，但当前仍不是容器级安全沙箱。

## 6. 当前结果

项目已经从“单次调用 LLM”演进为一个具备仓库理解、局部上下文读取、工具调用、受控编辑、代码验证、持久化 Session、跨模型记忆、完整 Diff 审查、可回滚补丁和运行监控的 Code Agent Demo。下一阶段最值得继续完善的是更精确的跨语言引用图、Git 原生工作区隔离、命令沙箱，以及基于真实编码任务集的成功率评测。
